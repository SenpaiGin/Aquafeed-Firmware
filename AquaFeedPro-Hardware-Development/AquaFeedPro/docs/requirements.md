# AquaFeed Pro requirements and capability matrix

**Status:** scoped product and architecture requirements baseline; **Updated:** October 3, 2026

This document records agreed scope and the capabilities a future feeder must declare and prove. ART-6 established the historical v1 contract. ART-7 D1 now defines the breaking v2 contract, shared fixtures, validators, and secure Supabase data foundation in this repository; both migrations are applied to the isolated AquaFeed development project and the full rollback SQL verification passed. API, app, simulator runtime, and firmware behavior are not implemented here. No physical feeder was inspected for this revision. Android is the current physical test target; iOS is deferred by the owner.

## Authority and status labels

- **Confirmed requirement / architecture decision** means an agreed product direction or required behavior. It is not evidence of implementation, a frozen wire contract, or hardware validation.
- **Simulator-only fixture** means a numerical example for simulator or test use. It is not a hardware limit, calibration, biological threshold, or performance guarantee.
- **Needs hardware evidence / unresolved decision** means the named responsible role must record a decision and the required evidence before the listed milestone or capability can be claimed. An unresolved value stays unknown; do not fill it with a plausible number.

## Product scope

**Confirmed requirement / architecture decision:** deliver a simulator-first Android and iOS app within the existing React Native, Expo, TypeScript, Expo Router, and Supabase direction. Preserve the four approved destinations and the monochrome bento design with Inter. The app must support multiple independently paired devices; selected-device readings, schedules, and history must remain bound to that device. See DESIGN.md for the complete visual and interaction specification.

| Page | Required behavior |
| --- | --- |
| Home | Show the selected device, connection and data freshness, available DO reading and trend graph, remaining-feed reading and percentage bar, next feeding, recent activity, and an explicit-confirmation manual-feed flow. A missing or unsupported capability is shown as unavailable. Refer to DESIGN.md for the graph and bar measurements. |
| Schedule | List, add, edit, enable, pause, and delete that device's recurring schedules. Show the device time zone, count, and requested-versus-applied save state. Only show controls supported by that device's validated profile. |
| History | Show manual and scheduled outcomes, filters, timestamps, requested amount, measured amount only when available, and distinct failure or uncertainty states. |
| Device | Pair, select, rename locally, inspect, and remove independently authorized devices. Show each device's connection, identity, and supported capabilities without implying unsupported hardware behavior. |

There is no email/password registration screen. The UI can be implemented and exercised against the simulator while physical capabilities remain unresolved. Simulation is not evidence of physical feeding success, calibration, accuracy, or safety.

## Two-nozzle operation and hardware handoff

**Owner-confirmed revision, October 2, 2026:** each device has two nozzles sharing a container continuously suspended from one load cell. The intended measurement is the shared container's weight change. Physical accuracy remains unverified; this records the design intent for later hardware work.

- Never dispense simultaneously. Nozzle 1 precedes nozzle 2 when both are selected or due at the same scheduled instant. Either nozzle can also dispense alone.
- Feed now opens Nozzle 1, Nozzle 2, or Both. The owner confirmed **a separate amount per nozzle** for Both. Confirm the device, nozzle selection, individual doses and order before submission; subsequent selection changes cannot retarget the request.
- Each recurring schedule belongs to one nozzle with its own time, repeat days, dose and enabled state. Same-time cross-nozzle schedules are valid and run 1 then 2. Duplicate/overlapping due slots on the same nozzle remain invalid.
- Reserve the whole admitted sequence, including nozzle transitions and weighing intervals, with one device-wide execution lock. This is an explicit ordered group, not a busy skip or unbounded queue. Unrelated collisions remain explicitly rejected/skipped; no hidden delayed feed or late cloud replay is introduced.
- Admit and persist a same-time group together. Define the second leg's deadline relative to its admitted sequence so normal completion of nozzle 1 does not incorrectly expire nozzle 2 under the old wake-up grace. Freeze bounded timing semantics in D1; real settling/runtime limits require hardware evidence. Reboot and clock correction never create catch-up sequences.
- Preserve a sequence identity and per-nozzle progress/outcomes. Semantic idempotency includes targets, order and each dose; changing them under the same key conflicts. Keep stable schedule occurrence identities: editing the nozzle or dose cannot bypass same-day deduplication.
- Conservative failure rule: halt remaining work if a nozzle faults, its stop is uncertain, or weighing evidence is invalid. Preserve completed, failed/unknown and not-started results separately. Partial success is not complete success. Never automatically resume an interrupted sequence or repeat its first nozzle.
- Record requested and measured amounts separately per nozzle. Attribute a shared-container weight delta only within that nozzle's exclusive, valid weighing interval. Missing/invalid measurements stay unavailable. Remaining feed is shared device inventory, not two independent nozzle stocks.

**Later hardware handoff:** verify permanent suspension, tare, capacity, refill handling, vibration/settling, mechanical/cable forces, safe stop, watchdog and interlock. Characterize each nozzle against independently weighed catches; retain per-nozzle calibration and configurable timing limits. Require the first nozzle stopped and a valid settled baseline before starting the second. Do not invent accuracy, settling delays or dose limits. Hardware inspection, firmware changes, GPIO actuation and bench trials remain deferred.

**Contract migration:** v1 carries one dose and no nozzle target. Its blanket busy-skip rule cannot satisfy same-time cross-nozzle schedules. D1 freezes the v2 request/event shapes, per-nozzle capabilities, partial outcomes, admission rules and version compatibility in [the contract](../contracts/README.md). Major 2 requires explicit nozzle targets and defines `PROTOCOL_UNSUPPORTED` for incompatible clients/devices; it never silently routes to a default nozzle or relies on an optional field legacy software ignores. V1 fixtures remain historical evidence, not proof of two-nozzle support. Both matching SQL migrations are applied to the isolated AquaFeed development project and the rollback check passed. Dependent runtime implementation is still pending.

## Installation identity, device identity, and access

**Confirmed requirement / architecture decision:** the app uses a Supabase anonymous Auth session internally as the identity of an app installation. This is a technical session, not an end-user account or registration experience. Each installation must obtain active membership for a device through pairing before it can read or control that device. A publishable Supabase project key identifies the project; it is not an installation session, device credential, or device authorization.

Each feeder has its own machine identity and revocable device credential, separate from every phone session. The phone never receives the feeder's reusable machine credential, a service-role key, or another project secret. A device credential authorizes that device's own API traffic only. Paired installations receive the same controller permissions in v1; this does not add user roles. Device aliases and locations are per installation so one phone's local rename does not rename another phone's device card.

The proposed pairing design uses a short-lived physical pairing window and a one-use challenge consumed once by the backend to create that installation's membership. M0/M2 settle and test the security contract: challenge-code entropy and attempt limits, an abstract local physical trigger, and credential provisioning and recovery semantics. The contract does not select the physical trigger or presentation method. M2 pairing, expiry, replay, consumption, membership, and revocation behavior is tested with simulator/backend fixtures. The actual physical trigger and presentation (such as a button or maintenance action and QR or readable code), on-device credential provisioning/storage, and physical recovery procedure require M6 prototype and bench evidence. The planning proposal's machine-token and pairing-window examples are not proof that a physical process exists or is secure.

Removing a device from this app revokes only this installation's membership and clears its local data. It does not erase the controller's applied schedules or feeding history, and it does not stop already applied local schedules; the app must explain that they may continue. Losing an installation requires physical maintenance recovery and re-pairing, not email recovery. The recovery procedure must revoke the lost installation's membership (or all memberships if it cannot be identified). Device credential rotation is a separate operator/device-maintenance operation.

## Shared command, schedule, and data rules

**Confirmed requirement / architecture decision:**

- Manual feeding requires confirmation bound to the named device, nozzle selection, order and individual doses. Later selection changes cannot silently retarget it. Do not offer feeding controls the device profile does not support.
- Keep the original idempotency key for a confirmed request. Retrying a network lookup or recovering status uses that same key and payload to find the original command; a different payload with that key is a conflict. Never create a new feed request as recovery from a timeout, expired command, or uncertain result.
- Preserve the distinctions queued, accepted, running, completed, failed, rejected, expired, and unknown. A queued response means the request was recorded; accepted means the controller journaled it; running requires start evidence. Rejected and confirmed-not-started expired commands did not feed. A possible-but-unresolved physical start is unknown, not expired.
- A device-reported completed cycle is not a measured amount. Keep requested amount, any explicitly labeled estimate, measured dispensed amount, and measurement quality separate. If no valid measurement exists, measured amount is unavailable/null. Do not present a requested or estimated amount as actual dispensing.
- Keep desired/requested configuration revisions separate from device-applied revisions. A save is confirmed only after the device acknowledges application. The controller validates and stages a complete schedule snapshot and switches it atomically between feeding operations; a rejected snapshot leaves the prior applied snapshot active.
- The controller executes acknowledged schedules locally without the app or internet. Persist applied configuration and a local occurrence ledger. Identify an occurrence by device, stable schedule identity, and local calendar date; editing a schedule must not create a second feed that day. Do not reuse a removed schedule identity. After reboot or a forward clock jump, mark overdue occurrences skipped rather than replaying them. Handle repeated daylight-saving times once, skip nonexistent local times, and require explicit time-zone changes.
- Manual and scheduled actions share one device-wide execution lock. Explicitly admitted Both/same-time cross-nozzle groups run 1 then 2 under that reservation; unrelated collisions are rejected/skipped, not silently queued. Persist sequence/command identity, each nozzle's run intent, schedule occurrence and events across reboot. Keep unacknowledged events until delivered; bound telemetry separately with lost intervals recorded.
- Telemetry retention deletion is disabled pending owner policy. D5 adds no scheduled deletion, archive, or retention job.
- An uncertain or expired action is never automatically actuated again. On reboot, outputs must be safe; an unfinished physical operation becomes unknown and may require local inspection. Cloud/API success and simulator completion are not claims that a real feeder dispensed food.
- Invalid, missing, uncalibrated, or stale measurements are unavailable or explicitly outdated, with quality/freshness context. They are never coerced to zero or a healthy status. Missing sensors do not by themselves mean the device is offline.

Carry this revision into the contract and simulator through D1 and its dependent feature deliveries. ART-6's frozen v1 remains the previous executable baseline; do not reopen that completed ticket or claim the new behavior is already implemented.

## Capability matrix and open evidence

Capabilities are per device and revision. The UI and backend must use an approved provisioning profile to validate advertised capabilities; a device cannot enable its own physical controls merely by claiming a capability. Unknown or mismatched profile data disables the affected control and is surfaced as unavailable. The owner listed below is a responsible role; a named person can be assigned later.

| Capability area | Requirement and current classification | Responsible role, evidence/disposition, and blocking milestone |
| --- | --- | --- |
| Dose modes and bounds | **Confirmed requirement / architecture decision:** declare supported dose modes per device. Use calibrated grams only when the physical profile validates the mode and its minimum, maximum, increment, accuracy, and maximum actuation time. A fixed portion is a distinct mode and must not be disguised as grams. **Unresolved:** real mode, gram bounds, step, accuracy tolerance, and runtime limit. | **Owner:** device/mechanical engineering and calibration/metrology. **Evidence:** identify the actual mechanism; record repeatable weighed trials across supported settings and operating conditions, plus jam/stall and stop behavior; approve per-device limits and calibration revision. **Blocks:** M0 contract/profile decision for how values are represented; M6 real actuation in any unproven mode. Until then, only simulator controls are enabled. |
| DO sensor availability and calibration | **Confirmed requirement / architecture decision:** each device declares whether DO monitoring is supported; valid values use mg/L and carry quality, freshness, and calibration context. Unsupported, missing, uncalibrated, or failed sensors display unavailable. **Unresolved:** sensor/interface, compensation, calibration method, and supported operating conditions. | **Owner:** sensor/instrumentation engineering. **Evidence:** identify the installed sensor/interface and compensation; document calibration against a suitable reference over the intended water conditions, repeatability, error, and invalid/fault behavior. **Blocks:** M0 capability/quality contract decision and M6 real DO readings or sensor-dependent claims. UI simulation and feeding that does not depend on DO can proceed. |
| Biological DO thresholds and feed interlock | **Confirmed requirement / architecture decision:** monitoring does not authorize a biological control rule. Show “within limits” only for fresh readings and explicitly configured, applicable limits. Do not invent a universal threshold or infer that low DO prevents feeding. **Unresolved:** biological thresholds and whether any DO condition blocks feeding. | **Owner:** aquaculture/domain specialist with product/architecture. **Evidence:** written, setup-specific basis covering the relevant species and operating conditions, approved limits, and an explicit decision on warning versus interlock. **Blocks:** M0 decision for any threshold-dependent contract behavior and M6 any real threshold-based warning/interlock claim. Other monitoring and feed behavior may proceed without such a rule. |
| Remaining feed and hopper capacity | **Confirmed requirement / architecture decision:** disclose what is measured. Show remaining grams, percentage, and capacity only when supported by calibrated device data; otherwise show unavailable. Do not estimate feed remaining from unverified motor runtime. **Owner-confirmed design:** the shared feed container is continuously suspended from one load cell. **Unresolved:** physical measurement validation, actual capacity, and low-feed threshold. | **Owner:** mechanical and sensor/instrumentation engineering. **Evidence:** identify the measured volume/component; establish capacity and calibration at empty, full, and representative intermediate levels; record repeatability and behavior with the intended feed. Approve any alert threshold separately. **Blocks:** M0 capability/profile representation and M6 real capacity, percentage, or low-feed claims. |
| Measured dispensing | **Confirmed requirement / architecture decision:** advertise measured-dispense support separately from dose control. Report an actual amount only from a valid measurement; otherwise leave it unavailable and retain cycle outcome separately. **Unresolved:** whether physical dispensing is measured and how measurement uncertainty is bounded. | **Owner:** mechanical and calibration/metrology engineering. **Evidence:** compare measured output with independently weighed catches over the supported dose range and repeated cycles; document resolution, uncertainty, and failure cases. **Blocks:** M0 capability semantics and M6 any claim of measured physical dispensing. A cycle-completed status can remain available without a measured amount. |
| Local scheduling and schedule count | **Confirmed requirement / architecture decision:** the controller, not the phone, cloud timer, or in-memory task, executes applied schedules offline and persists the occurrence ledger. Advertise the supported schedule count; validate edits against that count. **Unresolved:** real maximum schedule count and sustained local scheduler capacity. | **Owner:** firmware/device engineering. **Evidence:** measure capacity on the target controller and run persistence, reboot, time-change, collision, and sustained schedule tests at the declared limit. **Blocks:** M0 profile field/semantics; M6 the real supported count and local-scheduler claim. M4 UI can use simulator capabilities and adapt per device. |
| Clock, RTC, and uncertainty | **Confirmed requirement / architecture decision:** recurring times use the device time zone; events use UTC when wall time is trustworthy and preserve time quality. Track clock uncertainty and use a monotonic clock for elapsed runtime. Pause schedules when time is invalid or beyond the validated profile's uncertainty; do not replay missed feeds after reboot. **Unresolved:** RTC availability, holdover, synchronization method, drift, and acceptable uncertainty. | **Owner:** firmware and electrical engineering. **Evidence:** identify the clock source; measure drift/holdover across expected uptime and power-loss/reboot cases; verify sync, time-zone/DST changes, and uncertainty reporting against an approved schedule-safety limit. **Blocks:** M0 time/profile decisions; M6 real offline schedule execution and deadline-sensitive actuation. |
| Physical pairing, credentials, and recovery | **Confirmed requirement / architecture decision:** installation session, per-device machine credential, and per-installation active membership are separate identities. Use a short-lived one-use pairing contract; never use a permanent serial as a secret or expose reusable device credentials to the phone. **Unresolved at M0/M2:** challenge entropy and attempt limits, abstract physical trigger, and provisioning/recovery contract. **Unresolved for M6:** actual trigger and presentation method (button/maintenance action, QR/readable code), on-device credential provisioning/storage, and physical recovery procedure. | **Owner:** device security and firmware, with backend/security review. **Evidence:** at M0 document the threat-reviewed security contract, entropy/attempt limits, abstract trigger, and provisioning/recovery semantics; at M2 test pairing, expiry, replay/consumption, membership, and revocation with simulator/backend fixtures; at M6 verify the selected physical trigger/presentation, device credential handling, and recovery on the prototype. **Blocks:** M0 security-contract decisions and M2 simulator/backend pairing fixtures; only the actual physical implementation and evidence block M6, not M2 or app pages. |
| Actuator safe stop, watchdog, runtime, and cooldown | **Confirmed requirement / architecture decision:** persist intent before movement; use a lock shared by manual and scheduled feeds; enforce an independent maximum-runtime stop; de-energize safely on completion, error, crash, and reboot. Unresolved physical runs lock out another feed until inspected/reconciled. **Unresolved:** actuator type, safe electrical/mechanical state, watchdog implementation, runtime limit, and cooldown. | **Owner:** mechanical/electrical and firmware safety engineering. **Evidence:** document the actual actuator and stop path; test jam/stall, controller crash, watchdog timeout, power loss, restart, repeated operation, and manual/schedule collision; establish per-device runtime and cooldown limits. **Blocks:** M0 safety-profile representation and M6 all real actuation. This is a hard physical gate. |
| Telemetry timing and offline recovery | **Confirmed requirement / architecture decision:** device safety and already-applied schedules remain local during cloud/app outage. Use bounded network retry without coupling the actuator watchdog to networking; retain feeding events until acknowledged, then flush history in bounded batches with a fresh sample. Never replay all cloud commands after reconnect. **Unresolved:** actual sensor/sample cadence, sustainable sync/upload rate, backlog capacity, and connectivity behavior of the physical installation. | **Owner:** device/firmware and backend integration. **Evidence:** measure sustained operation at the declared profile; test network loss, long offline intervals, reboot, bounded backoff, duplicate delivery, outbox recovery, and stale/live ordering without losing feeding evidence. **Blocks:** M0 timing defaults/profile decision, M5 failure/handoff evidence, and M6 real-device sync/offline bench acceptance. |
| Per-device capability profile and validation | **Confirmed requirement / architecture decision:** capabilities and a revision are per device; backend validation constrains a device's report to its approved provisioning profile. Unsupported modes remain disabled; a simulator profile is explicitly marked simulated. **Unresolved:** real model/unit inventory, per-device capability values, and profile approval/change procedure. | **Owner:** device integration/firmware and platform security. **Evidence:** maintain a reviewed provisioning record for each hardware profile; compare reported capabilities and revision to that record; test missing, stale, unsupported, and mismatched values; preserve calibration per device. **Blocks:** M0 profile contract decision, M2 backend validation fixtures, and M6 real-device capability acceptance. |

M0 records and resolves contract-impacting decisions; it does not require fabricated physical values. For each open item, record date, responsible role, evidence, decision, affected profile/contract revision, and any remaining limitation. ART-46 physical inspection and M6 bench evidence are separate from this requirements task.

## Milestones and physical gates

Keep the master plan's milestone identifiers and meanings:

| Milestone | Exit focus |
| --- | --- |
| M0 | Contract baseline agreed; hardware unknowns explicitly tracked. |
| M1 | Native application shell and design system run on both platforms. |
| M2 | Secure backend, device pairing, and executable contract fixtures work. |
| M3 | Simulator operates through production-shaped APIs. |
| M4 | Four application pages complete against the simulator. |
| M5 | Failure, isolation, and build gates pass; hardware handoff package is ready. |
| M6 | Real feeder integration passes bench tests. This is the physical gate for real-device capability, calibration, timing, safety, pairing, and actuation claims. |
| M7 | Pilot and release gates pass. |

M1–M5 app/backend work can proceed with open hardware values represented as capabilities or unavailable data. Simulator completion is not physical success. A real control is enabled only for an approved per-device profile after its relevant M6 evidence passes; unvalidated features stay unavailable or disabled. M7 cannot substitute for missing M6 bench evidence.
